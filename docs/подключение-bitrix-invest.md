# Мероприятия по подключению Битрикс24 к «Инвестконтуру Кубани»

**Назначение:** чек-лист орг. и технических мер для перевода обмена Битрикс24 ↔ ДелаЮ из **sandbox** в промышленный режим.  
**Дата:** июль 2026 · **Версия:** 1.0  
**Связанные документы:** `docs/пояснительная-записка-invest-zapusk-2026.md`, `docs/подключение-smev-rgis-invest.md`  
**В продукте сейчас:** inbound webhook + outbound push реализованы; по умолчанию `sandbox=True` (исходящие пишутся в журнал, живой REST не вызывается). UI: `/invest/automation/`.

---

## 0. Что уже есть в системе (не начинать с нуля)

| Компонент | Статус | Где |
|-----------|--------|-----|
| Входящий webhook | Готов | `POST /api/invest/bitrix/webhook/<subsystem_code>/` + токен |
| Исходящий push | Готов (live при выключенном sandbox) | `push_project_to_bitrix` → `POST` на `bitrix_api_base` |
| Журнал событий | Готов | `InvestIntegrationEvent`, вкладка статусов автоматизации |
| Маппинг полей и стадий | Готов | `field_mapping`, `stage_mapping` в `InvestAutomationConfig` |
| Gate перед выгрузкой | Готов | `gate_before_outbound`: пакет, стоп-факторы, открытые задачи МО |
| Конфликт стадий | Готов | UI resolve: приоритет Битрикс или ДелаЮ |
| Песочница | **Включена по умолчанию** | Флаг `sandbox` |

**Не путать с СМЭВ:** Битрикс — облачный/коробочный CRM Агентства (обычно), заявки в Минцифры не нужны. Нужны доступы **владельца портала Битрикс24**, регламент master/slave и сетевой HTTPS.

## 1. Организационные мероприятия

### 1.1. Решения, которые зафиксировать письменно

| № | Решение | Зачем |
|---|---------|--------|
| 1 | **Кто master по сделкам привлечения?** Агентство в Битрикс / ДелаЮ / гибрид | Без этого дуплекс ломает данные |
| 2 | **Кто master после handoff в Департамент?** Обычно ДелаЮ (сопровождение), Битрикс — только статус/комментарий | Воронка `support` в контуре не должна откатываться стадиями CRM |
| 3 | Объём пилота: N сделок / 1 воронка / 1 ответственный | UAT |
| 4 | Персональные данные: что уходит в Битрикс (ИНН, телефон, вложения) | Согласие / политика |
| 5 | Режим запуска: сначала **только inbound** → потом outbound → потом full duplex | Снижение риска |

Рекомендуемая модель для края:

```text
Битрикс24 (Агентство)  --inbound-->  ДелаЮ (привлечение)
ДелаЮ (пакет готов)    --outbound-->  Битрикс24 (UF-поля + комментарий)
Handoff в Департамент  --только в ДелаЮ--  (стадии support не форсятся из CRM)
```

### 1.2. Роли и ответственность

| Роль | Организация | Зона |
|------|-------------|------|
| Владелец портала Битрикс24 | Агентство (типично) | Админ CRM, воронки, права, вебхуки |
| Функциональный заказчик обмена | Агентство + Департамент | Маппинг стадий, правила конфликтов |
| Админ инвестконтура | ИТ / `invest_admin` | `/invest/automation/`: URL, токен, флаги |
| Вендор ДелаЮ | ЮГИт | Доработка контракта REST при необходимости, UAT |
| ИБ | Заказчик | Allowlist IP, HTTPS, секреты, аудит |

### 1.3. Регламенты (минимум)

1. **Создание сделки в Битрикс** → в течение N минут появляется/обновляется проект в ДелаЮ.  
2. **Изменение стадии в Битрикс** → обновление стадии attraction **или** фиксация конфликта, если в ДелаЮ уже другая.  
3. **Стоп-лист** не создавать проекты: стадии/признаки `TEST`, `ARCHIVE`, `JUNK`, `LOSE` (и флаги `is_test` / `is_archive` в payload).  
4. **Обратная выгрузка** только при выполнении gate (или по решению админа `force`).  
5. **Эскалация:** кто смотрит журнал ошибок и dead-letter раз в день на пилоте.

### 1.4. Документы / «заявки» (не СМЭВ, но пакет согласований)

| Документ | Кто готовит | Содержание |
|----------|-------------|------------|
| Служебная записка / протокол о пилоте обмена | Агентство ↔ Департамент | Master/slave, пилот, сроки |
| Заявка админу Битрикс на **входящий вебхук** (исходящие события CRM → ДелаЮ) | Агентство | URL webhook ДелаЮ, события `ONCRMDEALADD` / `UPDATE` / `DELETE` (уточнить набор) |
| Заявка на **исходящий вебхук / приложение REST** | Агентство | Права `crm`, пользователь/токен для push из ДелаЮ |
| Заявка на **пользовательские поля (UF_*)** в сделке | Агентство + вендор | Список из раздела 3 |
| Заявка ИБ на **разрешение исходящего HTTPS** с сервера ДелаЮ на `*.bitrix24.*` | ИТ | Для live outbound |
| Заявка ИБ на **входящий HTTPS** к webhook ДелаЮ (и при необходимости allowlist IP Битрикс) | ИТ | Для inbound |
| Акт опытной эксплуатации обмена | Все стороны | До выключения `sandbox` |

## 2. Технические мероприятия: сервер и сеть

### 2.1. Со стороны «ДелаЮ»

| Мера | Детали |
|------|--------|
| HTTPS публичный URL | Webhook должен быть доступен из облака Битрикс24 (или из сети коробочного Б24) |
| Endpoint | `/api/invest/bitrix/webhook/invest-kk/` (код подсистемы уточнить в seed: `invest-kk`) |
| Токен | `bitrix_webhook_token` в автоматизации; генерируется в UI; передаётся в query/header по согласованному контракту |
| Allowlist IP | Поле `allowed_ips` в конфиге — заполнить IP исходящих запросов Битрикс (облако — диапазоны вендора; коробка — IP сервера CRM) |
| Исходящий доступ | С сервера ДелаЮ до `bitrix_api_base` (обычно `https://<portal>.bitrix24.ru/rest/...`) |
| Секреты | Токены не в git; ротация при увольнении админа CRM |
| Журнал | Мониторинг `InvestIntegrationEvent` (ошибки, retry, dead) |
| Backup | Конфиг автоматизации входит в бэкап БД |

Отдельный «сервер Битрикс» для ДелаЮ **не нужен**. Нужен только сетевой доступ и (при коробке Б24) согласование с админом CRM.

### 2.2. Со стороны Битрикс24

| Мера | Детали |
|------|--------|
| Портал | Облако или коробка; зафиксировать URL |
| Права администратора | Создание вебхуков и UF-полей |
| Исходящий вебхук CRM → ДелаЮ | URL + токен; события по сделкам нужной воронки |
| Входящий REST для ДелаЮ | URL вида `https://portal.bitrix24.ru/rest/<user_id>/<token>/` **или** обработчик приложения, который принимает JSON паспорта |
| Воронка пилота | Одна воронка «Привлечение» / согласованные `STAGE_ID` |
| Тестовые сделки | Отдельная стадия/признак в стоп-листе, чтобы не засорять контур |

### 2.3. Архитектура обмена

```text
[ Битрикс24 сделка ]
        |  outbound webhook (событие)
        v
[ HTTPS ] --> [ ДелаЮ webhook ] --> upsert InvestProject
                                      | pipeline (пакет, площадка…)
                                      v
                                 [ журнал событий ]

[ ДелаЮ проект готов по gate ]
        |  push (если sandbox=off)
        v
[ POST bitrix_api_base ] --> обновление сделки / UF / комментарий
```

**Текущий live-контракт outbound:** `httpx.post(bitrix_api_base, json={fields, passport, comment, attachments})`.  
Типовой webhook REST Битрикс (`crm.deal.update.json`) ожидает другой формат (`fields[TITLE]=...`). На пилоте выбрать один из путей:

| Вариант | Суть | Когда |
|---------|------|--------|
| **A. Прослойка на стороне Б24** | Локальный/облачный обработчик принимает JSON ДелаЮ и вызывает `crm.deal.update` | Быстрее без смены ДелаЮ |
| **B. Доработка ДелаЮ** | Коннектор сам вызывает `crm.deal.update` / `crm.deal.add` с UF | Предпочтительно для продакшена |
| **C. Входящий вебхук + робот** | Робот Битрикс забирает данные иначе | Обычно хуже для полного паспорта |

Зафиксировать вариант в протоколе пилота **до** выключения sandbox.

## 3. «Сведения» и поля: что настроить в Битрикс

### 3.1. Пользовательские поля сделки (создать в CRM)

Соответствуют исходящему контракту `build_bitrix_outbound_fields`:

| Код UF (логика) | Назначение | Тип (рекомендация) |
|-----------------|------------|--------------------|
| `UF_DELAYU_CODE` | Код проекта в ДелаЮ | Строка |
| `UF_DELAYU_FUNNEL` | Воронка attraction/support | Список / строка |
| `UF_CADASTRE` | Кадастровый номер | Строка |
| `UF_AREA_HA` | Площадь, га | Строка / число |
| `UF_VRI` | ВРИ | Строка |
| `UF_RIGHT_TYPE` | Вид права | Строка |
| `UF_ADDRESS` | Адрес | Строка |
| `UF_ENCUMBRANCES` | Обременения | Текст |
| `UF_COORDS` | Координаты | Строка |
| `UF_SUPPORT` | Меры поддержки | Текст |
| `UF_READY` | Готов к выгрузке (gate) | Да/Нет |
| `UF_COMPLETENESS` | % полноты | Число |

Фактические ID полей в Битрикс (`UF_CRM_…`) занести в `field_mapping` / доработку коннектора.

### 3.2. Входящие поля (сделка → ДелаЮ)

Прямые ключи, которые уже понимает ingest (плюс маппинг):

| Поле Битрикс / payload | Поле ДелаЮ |
|------------------------|------------|
| `ID` / `bitrix_id` | `external_ids.bitrix_id` (идемпотентность) |
| `STAGE_ID` / `bitrix_stage` | Стадия через `stage_mapping` |
| `TITLE` → через mapping `name` | `InvestProject.name` |
| Инвестор, отрасль, контакты, сумма, рабочие места | Соответствующие поля проекта |
| `investor_inn` | `external_ids.investor_inn` + дедуп |
| `cadastral_number` | Pipeline площадки |
| `organization_code` | Привязка к org (МО/агентство) |
| `ASSIGNED_BY_ID` / owner hint | Подсказка agency/dept |

Обязательно согласовать **таблицу `field_mapping`** в UI «Автоматизация → Mapping» и версию `contract_version`.

### 3.3. Маппинг стадий (`stage_mapping`)

Пример логики (конкретные `STAGE_ID` взять из воронки портала):

| STAGE_ID в Битрикс | Воронка ДелаЮ | Стадия ДелаЮ |
|--------------------|---------------|--------------|
| NEW / … | attraction | lead |
| PREPARATION / … | attraction | qualify |
| … | attraction | site_pick |
| … | attraction | package_ready |
| … | attraction | handoff |
| WON / … | — | не форсить `support` из CRM |

Правило продукта: переход в **support** только через **InvestHandoff**, не прямым маппингом из Битрикс.

Стоп-лист (не создавать/пропуск): `TEST`, `ARCHIVE`, `JUNK`, `LOSE`.

### 3.4. Gate перед outbound (что должно быть закрыто)

Выгрузка блокируется, если есть:

- пустые обязательные поля: name, investor_name, organization, industry;  
- неполный обязательный пакет;  
- открытые/просроченные задачи МО;  
- открытые/блокирующие стоп-факторы.

Это сознательная дисциплина: в Битрикс не улетает «сырой» проект.

## 4. Пошаговый план внедрения

### Этап B0 — подготовка (3–5 рабочих дней)

1. Протокол master/slave и пилот.  
2. Выгрузка списка стадий воронки из Битрикс.  
3. Создание UF-полей.  
4. Назначение админов и ответственных за журнал.

### Этап B1 — inbound only (1–2 недели)

1. В ДелаЮ: сгенерировать токен, сохранить, скопировать webhook URL.  
2. В Битрикс: исходящий вебхук на URL ДелаЮ (события сделок пилотной воронки).  
3. Флаги: `bitrix_inbound=True`, `bitrix_outbound=False`, `sandbox=True`.  
4. Прогнать 5–10 тестовых сделок (в т.ч. стоп-лист и дубли по ИНН/bitrix_id).  
5. Проверить дедуп, маппинг, конфликты стадий.  
6. Заполнить `allowed_ips` при требовании ИБ.

### Этап B2 — outbound sandbox (3–5 дней)

1. Включить `bitrix_outbound=True`, оставить `sandbox=True`.  
2. С карточки проекта — «Выгрузить в Битрикс»: событие в журнале без REST.  
3. Проверить gate blockers и паспорт (`build_passport`).  
4. Согласовать вариант A/B/C для live REST.

### Этап B3 — outbound live на пилоте (1–2 недели)

1. Указать `bitrix_api_base` (обработчик или доработанный endpoint).  
2. ИБ: исходящий HTTPS.  
3. Выключить `sandbox` **только** для пилотных сделок (или отдельный тестовый портал).  
4. Сверить UF на сделке с данными ДелаЮ.  
5. Включить `bitrix_full_duplex` после стабильного inbound+outbound.  
6. Акт опытной эксплуатации → промышленный режим.

### Этап B4 — промышленная эксплуатация

1. Регламент ежедневного просмотра ошибок журнала.  
2. Ротация токенов (квартал / по инциденту).  
3. Запрет ручного «тихого» изменения `bitrix_id` без аудита.  
4. Обучение сотрудников Агентства: какие поля обязательны в CRM, чтобы контур не падал на validation.

**Ориентир календаря:** **3–6 недель** при готовом портале и админе CRM (существенно быстрее СМЭВ/РГИС).

## 5. Чек-лист настроек в UI ДелаЮ (`/invest/automation/`)

### Подключение

- [ ] `bitrix_api_base` заполнен (для live)  
- [ ] `bitrix_webhook_token` сгенерирован и передан в Битрикс  
- [ ] Webhook URL скопирован админу CRM  
- [ ] `contract_version` зафиксирован (например `v1`)  
- [ ] `allowed_ips` согласован с ИБ  

### Компоненты (флаги)

| Флаг | Пилот inbound | Пилот duplex | Прод |
|------|---------------|--------------|------|
| `bitrix_inbound` | on | on | on |
| `bitrix_outbound` | off → on | on | on |
| `bitrix_full_duplex` | off | on | on |
| `sandbox` | on | off (после UAT) | off |
| `gate_before_outbound` | on | on | on |

### Mapping

- [ ] `field_mapping`: все ключевые UF/поля CRM  
- [ ] `stage_mapping`: все стадии пилотной воронки  
- [ ] Сброс к defaults только осознанно (кнопка reset)

### Статусы

- [ ] Есть успешные `deal.upsert`  
- [ ] Нет роста dead-letter  
- [ ] Конфликты стадий разбираются по регламенту

## 6. Риски и ответы

| Риск | Митигация |
|------|-----------|
| Двойные проекты | Идемпотентность по `bitrix_id`; дедуп по ИНН/названию |
| Порча воронки сопровождения | Запрет маппинга support из CRM; только handoff |
| Утечка ПДн во вложениях | Gate + политика: какие файлы пакета пушить |
| Облако Б24 недоступно / смена токена | Алерт по журналу; runbook ротации |
| Несовместимый REST-формат | Вариант A (прослойка) или доработка ДелаЮ до `crm.deal.update` |
| Тестовые сделки в боевом контуре | Стоп-лист стадий + отдельная тестовая воронка |

## 7. Отличие от СМЭВ/РГИС (для руководителя)

| | Битрикс24 | СМЭВ / РГИС |
|--|-----------|-------------|
| Заявки в Минцифры / ДИиС | Нет | Да |
| Срок орг. контура | Дни–недели | Месяцы |
| Инфраструктура | HTTPS + токены | Адаптер, канал, УКЭП / соглашение ГИС |
| Блокирует этап 1? | Нет (контур работает без duplex) | Нет |
| Владелец доступа | Админ портала Агентства | УВ СМЭВ / оператор РГИС |

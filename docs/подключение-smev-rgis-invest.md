# Подключение СМЭВ и РГИС к «Инвестконтуру Кубани»

**Назначение:** детальный чек-лист для департамента / агентства / ИТ: какие **заявки**, какой **сервер**, какие **виды сведений** нужны, чтобы перевести консоль СМЭВ и слот РГИС из mock/stub в промышленный обмен.  
**Дата:** июль 2026 · **Версия:** 1.0  
**Связанные документы:** `docs/пояснительная-записка-invest-zapusk-2026.md`, `docs/подключение-bitrix-invest.md`, дизайн этапа 1  
**Важно:** актуальные формы и коды ВС всегда сверять в [ЛК УВ / ЕСКС](https://info.gosuslugi.ru/) и у оператора РГИС КК — ниже типовой маршрут, не замена регламентов Минцифры/Росреестра/края.

В продукте сейчас:
- СМЭВ — mock-консоль; при `smev_live` заявка уходит в статус ожидания шлюза (**адаптер не подключён**);
- РГИС — пункт пакета + stub-флаг `rgis_connector=False`;
- демо-типы сведений в коде: `egrn-basic`, `isogd-zone`, `rgis-intersections`.

## 0. Два разных контура (не путать)

| | **СМЭВ (федеральный)** | **РГИС Краснодарского края** |
|--|------------------------|------------------------------|
| Что это | Межведомственный обмен РФ (в т.ч. ЕГРН Росреестра) | Региональная ГИС края |
| Правовая опора | 210-ФЗ, правила/методички СМЭВ, 218-ФЗ + Порядок Росреестра П/0149 | Постановление губернатора КК [№ 921 от 15.12.2021](https://krasnodar-gov.ru/doc/62313) |
| Оператор / точка входа | Минцифры РФ, СЦ [`sc.digital.gov.ru`](https://sc.digital.gov.ru), ЛК УВ | Уполномоченный орган — **Департамент информатизации и связи КК**; соглашение об информационном взаимодействии |
| Типовой канал | Защищённый канал + Адаптер СМЭВ3 (SOAP/XML) | Соглашение + доступ к слоям/API/витрине (конкретный протокол — у оператора РГИС) |
| Для инвестконтура | Выписки/сведения ЕГРН (и при необходимости иные ВС) | Пересечения, зоны, ограничения, региональные слои площадок |

**Рекомендация по ролям:** заявитель и владелец ИС в СМЭВ — **Департамент (РОИВ)** или уже подключённая ИС края. Агентство (АНО) чаще работает как пользователь контура, а не как самостоятельный УВ СМЭВ — иначе нужен отдельный правовой статус и регистрация.

## A1. Сначала выяснить «уже подключены или с нуля»

| Вопрос | Если ДА | Если НЕТ |
|--------|---------|----------|
| Организация уже УВ СМЭВ3? | Переходим к регистрации **новой ИС** / доступу к ВС | Полный цикл шагов 1–12 ЕСКС |
| Есть Адаптер СМЭВ3 (или шлюз) в контуре края? | Интегрируем «ДелаЮ» к существующему адаптеру | Закупка/развёртывание Адаптера + канал |
| Уже есть доступ к ВС ЕГРН Росреестра? | Добавляем ИС инвестконтура в доступ / маппинг | Заявка на доступ к конкретному ВС |
| Есть УКЭП организации для СМЭВ? | Используем для подписи сообщений адаптера | Выпуск в аккредитованном УЦ |

Для **РОИВ / ОМСУ** регистрация участника в средах СМЭВ часто идёт в **автоматическом режиме** (см. примечание ЕСКС к шагу 5). Для организаций **не** из перечня ОИВ — отдельные заявки через СЦ.

## A3. Сервер и инфраструктура СМЭВ

Минимально нужны **три логических контура** (могут быть на разных ВМ):

```text
[ Пользователи ДелаЮ ] → [ Сервер приложения ДелаЮ ]
                              ↓ (внутренняя сеть)
                         [ Адаптер СМЭВ3 + СКЗИ/ЭП ]
                              ↓ (защищённый канал)
                         [ СМЭВ тест / прод ]
```

### A3.1. Сервер приложения «ДелаЮ» (уже для этапа 1)

| Параметр | Ориентир |
|----------|----------|
| ОС | Ubuntu 24.04 / согласованная ОС заказчика |
| ПО | Nginx, Gunicorn, PostgreSQL 16, HTTPS |
| Сеть | Не обязан «видеть» СМЭВ напрямую — только адаптер во внутренней сети |
| Роль | UI запросов, журнал `InvestSmevRequest`, применение ответа к площадке/пакету |

### A3.2. Сервер (ВМ) Адаптера СМЭВ3

| Параметр | Типовые требования (уточнять по дистрибутиву адаптера) |
|----------|--------------------------------------------------------|
| Назначение | Подпись/проверка конвертов, очередь запросов/ответов, транспорт SOAP/XML к СМЭВ |
| ОС | Обычно Linux; следовать инструкции дистрибутива Адаптера СМЭВ3 с ЕСКС |
| CPU/RAM/Disk | Не ниже рекомендаций вендора адаптера; заложить рост очереди при массовых запросах по кадастрам |
| ПО | JDK (версия по инструкции), Адаптер СМЭВ3, средства работы с сертификатами |
| ЭП | Сертификат УКЭП организации / ИС; хранение ключей по политике ИБ (HSM/носитель — по требованиям) |
| Интеграция с ДелаЮ | REST/SOAP адаптера **или** обмен через БД/файловый каталог (выбрать один контракт и зафиксировать в ТЗ) |
| Логи | Ротация, аудит correlation_id / message_id (в продукте уже заложены поля) |

### A3.3. Защищённый канал до ИЭП / СМЭВ (продуктив)

По [ЕСКС](https://info.gosuslugi.ru/articles/%D0%9A%D0%B0%D0%BA_%D1%81%D1%82%D0%B0%D1%82%D1%8C_%D1%83%D1%87%D0%B0%D1%81%D1%82%D0%BD%D0%B8%D0%BA%D0%BE%D0%BC_%D0%B2%D0%B7%D0%B0%D0%B8%D0%BC%D0%BE%D0%B4%D0%B5%D0%B9%D1%81%D1%82%D0%B2%D0%B0_%D0%B2_%D0%A1%D0%9C%D0%AD%D0%92%3F/): организовать защищённый канал от инфраструктуры организации до инфраструктуры электронного правительства; см. также требования к СПД участников и приложение к Правилам СМЭВ.

На практике у субъектов РФ часто уже есть:

- региональный **узел / шлюз СМЭВ** (Департамент информатизации),  
- или сертифицированные комплексы класса **ViPNet EDI / Soap Gate** и аналоги для TLS ГОСТ и ЭП.

**Действие для проекта:** не закупать «второй СМЭВ с нуля», пока ИТ края не подтвердит: *куда подключать новую ИС — к существующему шлюзу или нужен отдельный адаптер.*

| Что запросить у ДИиС / ИБ края | Зачем |
|-------------------------------|-------|
| Есть ли действующий Адаптер/шлюз СМЭВ3 | Переиспользование |
| Как регистрируют новую ИС ОИВ | Формы, сроки |
| Требования к сегменту сети (DMZ, ViPNet и т.д.) | Размещение адаптера |
| Кто выпускает/держит сертификат ЭП для СМЭВ | Закупка носителей/HSM |
| Тестовые УЗ и стенд | Пилот ЕГРН |

### A3.4. Сертификаты и ключи

Для продуктивной среды СМЭВ3 нужны ([выбор формата взаимодействия, ЕСКС](https://info.gosuslugi.ru/articles/%D0%92%D1%8B%D0%B1%D0%BE%D1%80_%D1%84%D0%BE%D1%80%D0%BC%D0%B0%D1%82%D0%B0_%D0%B2%D0%B7%D0%B0%D0%B8%D0%BC%D0%BE%D0%B4%D0%B5%D0%B9%D1%81%D1%82%D0%B2%D0%B0/)):

1. защищённый канал;  
2. сертификат электронной подписи от УЦ;  
3. ИС или Адаптер СМЭВ3.

Отдельно: рабочее место администратора адаптера, процедуры перевыпуска сертификата, ответственный за ЭП.

### A4.1. Приоритет P0 (обязателен для пакета «ЕГРН»)

| Потребность | Канал | Комментарий |
|-------------|-------|-------------|
| Градостроительные сведения / зоны (слот `isogd`) | Часто **не** один федеральный ВС: ИСОГД МО / региональные сервисы / ручная загрузка | В продукте mock `isogd-zone`; live — отдельное ТЗ |
| Кадастровый план территории, координаты | Отдельные ВС Росреестра (уточнять каталог) | Для выкопировок; прямая массовая выгрузка KPT в этапе 1 не закладывалась |
| Иные ОИВ (обременения сетей и т.п.) | ВС соответствующих ведомств | Пункт пакета `oiv` |

### A4.3. Что писать в заявке на доступ к ВС (черновик формулировок)

- **Потребитель:** [полное наименование ОИВ], ИС «[название зарегистрированной ИС]».  
- **Цель:** обеспечение полномочий по сопровождению инвестиционных проектов / подбору земельных участков; формирование комплекта документов по объекту недвижимости.  
- **Основание:** [положение о департаменте / НПА / поручение]; обработка в интересах исполнения функций органа власти.  
- **Состав обмена:** запрос по кадастровому номеру ЗУ; получение сведений/выписки; хранение в ИС с разграничением доступа.  
- **Среды:** тест, затем прод.  
- **Объём:** оценка N запросов/сутки на пилоте и на полном контуре.

### A4.4. Маппинг ответа СМЭВ → поля инвестконтура

| Поле площадки / пакета | Источник в ответе ЕГРН (логически) |
|------------------------|-------------------------------------|
| `cadastral_number` | Кадастровый номер (ключ запроса) |
| `address` | Адрес / описание местоположения |
| `area_ha` | Площадь |
| `land_category` | Категория земель |
| `vri` | Виды разрешённого использования |
| `right_type` | Вид права / правообладатель (по политике ПДн — маскирование) |
| `encumbrances` | Ограничения / обременения |
| Пакет `egrn` | Файл выписки + статус `attached` |
| `InvestStopFactor` | Правила на критичные обременения |

Точный XPath/JSON Path фиксируется после выбора версии ВС.

## A5. Работы вендора «ДелаЮ» после появлении доступов

1. Контракт с Адаптером (очередь / API).  
2. Сборка XML-запроса по XSD выбранного ВС.  
3. Разбор ответа, валидация schema, статусы вместо `LIVE_PENDING`.  
4. Хранение сырого конверта + протокол (уже есть задел UI).  
5. Переключение флагов автоматизации; UAT на 5–10 кадастрах.  
6. Регламент повторных запросов, таймаутов (в модели — `timeout_at`), ошибок поставщика.

**Оценка разработки коннектора** (после готового адаптера и доступа к ВС): ориентир **4–8 недель** календаря на P0 ЕГРН, не включая орг. сроки СМЭВ.

# Часть B. РГИС Краснодарского края

## B1. Правовая и организационная рамка

По [постановлению губернатора КК № 921 от 15.12.2021](https://krasnodar-gov.ru/doc/62313):

- уполномоченный орган по координации РГИС КК — **Департамент информатизации и связи Краснодарского края**;  
- ОИВ и госучреждения из перечня обеспечивают **заключение соглашения об информационном взаимодействии** с уполномоченным органом по использованию РГИС, в т.ч. по **обмену пространственными данными**.

Отдельно в крае ведутся работы по выносу данных РГИС в **витрины данных** для межведомственного обмена (см. закупки на внедрение ПО витрин из РГИС КК) — возможный технический путь «не прямой API ГИС, а витрина / СМЭВ4».

**Вывод:** подключение РГИС — это в первую очередь **соглашение с ДИиС КК** + техническое приложение (состав слоёв, протокол, контур безопасности), а не «просто API-ключ из интернета».

## B2. Заявки и документы по РГИС

| № | Документ / действие | Адресат | Содержание |
|---|---------------------|---------|------------|
| 1 | Служебная записка / инициатива о подключении ИС «Инвестконтур» к РГИС | Руководство департамента → ДИиС | Цель, перечень слоёв, ответственные |
| 2 | **Соглашение об информационном взаимодействии** (или доп. к существующему) | ДИиС ↔ Департамент инвестиций / экономика | Обмен пространственными данными, права на использование |
| 3 | Приложение: **перечень информационных ресурсов / слоёв** | ДИиС / оператор РГИС | См. B4 |
| 4 | Приложение: **регламент обмена** (частота, формат, ответственные, инциденты) | Обе стороны | Online API / файловый / витрина |
| 5 | Заявка на **учётные записи / техническую УЗ / VPN** | Оператор РГИС | Доступ к стенду и прод |
| 6 | При необходимости — заявка на размещение интеграции в **сегменте ГИС/аттестованном контуре** | ИБ края | Если данные имеют особый статус |
| 7 | Акт опытной эксплуатации обмена | Заказчик + оператор + вендор | До включения `rgis_connector` |

Если Агентство тоже получает доступ к слоям — либо через ИС Департамента, либо отдельное соглашение (решает ДИиС).

## B3. Сервер и инфраструктура РГИС

РГИС обычно **не требует** отдельного «адаптера СМЭВ», но требует сетевого и прикладного контура:

```text
[ ДелаЮ ] ←→ [ Коннектор РГИС (модуль / сервис) ] ←→ [ API / WMS-WFS / витрина РГИС КК ]
                      ↑
              VPN / выделенная сеть края
```

| Компонент | Назначение | Запросить у оператора |
|-----------|------------|------------------------|
| Доступ к **тестовому** контуру РГИС | Отладка без боя | URL, логин, ограничения |
| Доступ к **прод** | Боевые пересечения | Квоты, SLA |
| Протокол | WMS/WFS, REST JSON, файловый GeoJSON/GML, витрина СМЭВ4 | Что реально открыто для ОИВ |
| Сервис коннектора | Может жить на той же ВМ, что ДелаЮ, или отдельный worker | CPU под гео-операции |
| Хранилище кэша | Локальный кэш пересечений (аналогично store МНП) | Диск, TTL обновления |
| Учётная запись сервиса | Не личная УЗ сотрудника | Ротация паролей/токенов |

**МНП (`mnp.economy.gov.ru`)** уже используется контуром как live-источник генплана — это **не замена РГИС КК**. РГИС даёт региональные слои и официальный контур края; МНП — федеральный НСПД/генплан.

---

## B4. Сведения / слои РГИС, нужные инвестконтуру

Минимальный набор для закрытия пункта пакета `rgis` и стоп-факторов:

| Приоритет | Слой / сведения | Зачем в контуре |
|-----------|-----------------|-----------------|
| P0 | Границы ЗУ / кадастровая подложка (если отдаётся) | Привязка площадки |
| P0 | ООПТ, водоохранные, санитарно-защитные и иные **зоны с особыми условиями** | Стоп-факторы, блок «ограничения» |
| P0 | Территориальные зоны / градостроительное зонирование (если в РГИС, не только ИСОГД МО) | Проверка ВРИ/допустимости |
| P1 | Инженерная инфраструктура, сети (если открыто ОИВ) | Оценка обеспеченности |
| P1 | Инвестплощадки / индустриальные парки (если ведутся в РГИС) | Сверка с реестром площадок |
| P2 | Ортофото, ЦМР и пр. | Картография, не обязательно для пакета |

В продукте демо-тип `rgis-intersections` («РГИС: пересечения и ограничения») — целевой сценарий: **по геометрии/кадастру площадки вернуть список пересечений + критичность**.

Формулировка в приложении к соглашению (пример):

> Обеспечить информационное взаимодействие ИС «Инвестконтур Кубани» с РГИС Краснодарского края в части предоставления потребителю [Департамент] сведений о пересечении объекта (земельного участка / площадки) с слоями: [перечень], в машиночитаемом виде (GeoJSON/GML/атрибутивная таблица), с идентификаторами объектов и датой актуальности, с периодичностью не реже [раз в сутки / online].

## B5. Альтернативные технические пути (выбрать с ДИиС)

| Путь | Когда уместен | Плюсы / минусы |
|------|---------------|----------------|
| **Прямой API / WFS РГИС** | Оператор выдаёт сервис ОИВ | Быстрее для карты; нужна квота и ИБ |
| **Витрина данных края** | Данные уже выносят из РГИС в витрину | Единый стандарт; возможна задержка актуальности |
| **СМЭВ4 / РЗ** | Если край публикует региональные данные как витрину СМЭВ4 | Единый федеральный транспорт; отдельное типовое ПО «Агент СМЭВ4» |
| **Файловый обмен** (GeoPackage/SHP по регламенту) | Пока нет API | Проще орг.; хуже online |

Для инвестконтура предпочтителен **online или суточный** обмен P0-слоёв; файловый — допустим на пилоте.

---

## B6. Работы вендора после соглашения

1. Реализация `rgis_connector`: запрос пересечений → запись в `external_ids` / стоп-факторы / пакет `rgis`.  
2. UI: статус последнего обмена, кнопка «Обновить из РГИС».  
3. Согласование CRS (обычно местная / WGS84) с картой Яндекс + МНП.  
4. Включение флага `rgis_connector=True` после акта.

Оценка разработки при стабильном API: **3–6 недель**; при файловом пилоте — быстрее прототип, дольше эксплуатация.

# Часть C. Совместный календарь и ответственность

| Этап | СМЭВ | РГИС | Срок (ориентир) |
|------|------|------|-----------------|
| 0. Решение руководства | Владелец ИС = Департамент | Инициатива соглашения с ДИиС | 1–2 нед. |
| 1. Заявки / соглашения | ЕСИА, СЦ, регистрация ИС, доступ к ВС ЕГРН | Соглашение + перечень слоёв | **1–3 мес.** (орг.) |
| 2. Инфраструктура | Канал, адаптер, сертификаты | VPN/УЗ, тестовый доступ | Параллельно 2–6 нед. |
| 3. Разработка коннекторов | ДелаЮ ↔ Адаптер ↔ ЕГРН | ДелаЮ ↔ РГИС | 4–8 + 3–6 нед. |
| 4. Пилот | 5–10 кадастров | 1–2 МО, набор слоёв P0 | 2–4 нед. |
| 5. Прод | `smev_live` | `rgis_connector` | После актов |

**Критический путь** почти всегда — **организационные заявки и соглашение**, не код.

### Матрица ответственности (RACI, кратко)

| Работа | Департамент | ДИиС / ИТ края | Агентство | Вендор ДелаЮ |
|--------|-------------|----------------|-----------|--------------|
| Заявки СМЭВ / основание | A/R | C | I | C |
| Канал и адаптер | C | A/R | I | C |
| Соглашение РГИС | A/R | A/R | C | I |
| Перечень слоёв/ВС | A | C | C | C |
| Коннекторы в продукте | C | I | I | A/R |
| Приёмка пилота | A | C | C | R |

A — accountable, R — responsible, C — consult, I — inform.
